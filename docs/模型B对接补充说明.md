# net_V FPGA 推理服务 —— 模型 B 对接补充说明（已确认稿）

> 给负责模型 B / 仿真环境的同学。我们已在 ZCU104 上部署 net_V 模型，
> 提供 UDP 推理服务。本文说明在"模型 B 阻塞循环内调用"模式下如何使用，
> 末尾根据现有 N=20 外层策略、内层接口代码和 UDP 模拟结果逐项给出确认答复。
> 协议字段细节见同目录《ethernet_protocol.md》，参考客户端见 udp_client.py。

## 1. 使用模式的变化

net_V 在模型 B 的循环中被**同步调用**：B 产生 7 维输入 → 等我们结果 →
继续算 → 再调用。即每次调用都是阻塞的，总耗时 ≈ 循环次数 × 单次往返时延。

## 2. 调用方式（协议不变）

- 板端 UDP 服务端：`192.168.1.10:5000`（固定 IP 无 DHCP；迁到你的环境时可改）
- 请求 36B（小端）：`magic=0x4E565231 | u32 seq | 7×float32 原始输入`
  （顺序 h0, I0, Δh, ΔI, ΔΩ, fmax, tf；单位 km/rad/km/rad/rad/m·s⁻²/s）
- 应答 20B：`magic=0x4E565232 | seq | float32 ΔV(m/s) | u32 status | u32 infer_us`
- **直接发原始物理量**，归一化在板端完成。
- 链路自检：magic=0x4E434B00 的包原样弹回（建议每条完整路线求解开始前发一次）。

## 3. 调用纪律（请务必实现）

1. **超时重发**：UDP 会丢包，阻塞循环中丢包=死等。建议：发出后 50ms 未收到
   应答 → 用原 seq 重发，最多 3 次，仍失败则报错退出。重发安全（同输入幂等）。
2. **串行调用**：不要并发发送多个请求；上一个应答收到（或超时重发耗尽）后再发
   下一个。应答按 seq 对账。
3. **检查 status**：应答 status 的 bit0=1 才有效；为 0 表示板端异常
   （如板子重启后权重未加载），应中止并报错。
4. 非法包（长度/magic 不符）板端直接丢弃不回包——你会以超时形式感知。

参考实现（Python，含打包/超时/统计）：同目录 `udp_client.py`，
可直接当库用或照抄逻辑。

## 4. 性能预算（实测）

| 项 | 数值 |
|---|---|
| PL 推理 | 恒 826 µs |
| 单次 UDP 往返（RTT） | 平均 ~1.1 ms（直连网线实测） |
| 估算公式 | 一轮总耗时 ≈ 循环次数 × 1.1ms + 模型 B 自身耗时 |

例：1,000 次循环 ≈ 1.1s；10,000 次 ≈ 11s；100,000 次 ≈ 110s。
如果这个量级不满足你们需求，我们再谈优化（有空间）。

## 5. 精度与适用范围

- ΔV 部署误差：vs 浮点模型 ≤1.5 m/s（典型 <0.5），远低于网络自身 ~2% 误差
- 输入须在包络内：h0∈[400,800]km、I0∈[1.047,1.396]rad、Δh∈[-400,400]km、
  ΔI∈[-0.0873,0.0873]rad、ΔΩ∈[-π,0]rad、fmax∈[5e-4,5e-3]m/s²、tf∈[0,3.15e7]s
- **仅预测非奇异转移**；奇异场景请不要查询（结果无意义）

## 6. 模型 B 对接内容确认

### 6.1 整体调用关系

对接关系成立。模型 B 指当前 N=20 的外层 MRSPP 策略网络，`net_V` 是每条候选边的内层速度增量预测器。电脑端输入一个包含 20 个待访问目标的实例，随机选定一个起点，并把该起点移动到局部索引 0。起点选择本身不产生速度增量，也不调用板端。随后执行 19 层递归。

第 k 层剩余 r 个未访问目标。每个目标分别与 1、9、17 和 25 d 四档转移时间组合，因此本层需要计算 4r 条候选边。电脑端完成 J2 长期项传播并生成 7 维原始物理输入。每条输入通过 UDP 同步发送至板端。板端返回 ΔV 后，电脑恢复当前层的候选 ΔV 张量，构造即时代价特征和动作掩码，再由外层策略选择一个目标时间联合动作。

完整 Greedy 路线的候选边数量为

$$
4\sum_{r=1}^{19}r=760.
$$

因此，一条 N=20 Greedy 路线会同步调用 `net_V` 760 次。调用次数随层数依次为 76、72、68、64、60、56、52、48、44、40、36、32、28、24、20、16、12、8 和 4。

### 6.2 输入字段

7 维字段与当前电脑版内层模型一致。

| 字段 | 当前模型计算 | 单位 | 确认状态 |
|---|---|---|---|
| h0 | 出发目标半长轴减地球半径 | km | 一致 |
| I0 | 出发目标倾角 | rad | 一致 |
| Δh | 到达高度减出发高度 | km | 一致 |
| ΔI | 到达倾角减出发倾角，保留正负号 | rad | 一致，现稿已修正包络 |
| ΔΩ | J2 传播后到达 RAAN 与出发 RAAN 的圆周主值间隔，取负绝对值 | rad | 一致 |
| fmax | 小推力模型参数，当前固定为 0.0025 | 原模型量纲 | 一致，按原值发送 |
| tf | 候选转移时间 | s | 一致 |

电脑发送原始 FP32 物理量。Scaler 标准化和定点量化由板端完成。板端输出的 ΔV 单位为 m/s，模型 B 收到后乘 0.001 转换为 km/s，并沿用当前代价特征、累计代价和动作掩码代码。

### 6.3 起点与目标编号

当前外层模型按局部目标 0 为固定起点训练。运行时先在输入的 20 个目标中随机选择起点，再同步重排轨道根数、J2 漂移特征和目标 ID，使该目标成为局部目标 0。程序保存 `local_to_global` 映射，完整路线生成后恢复原目标 ID。

随机起点属于外部给定条件。策略仍执行 19 次目标时间联合决策，因此可以直接使用现有训练检查点。

### 6.4 协议实现

请求格式`<II7f`和应答格式`<IIfII`已经由`udp_client.py --selftest`验证。请求长度、应答长度、小端字节序、magic、seq、status和错误包拒绝逻辑均通过。

应答 magic 的正确值为`0x4E565232`。原待确认稿中的`0x4E563252`属于文字错误，现已修正。

主机接收应答时需要同时验证来源 IP 和端口、20 B 长度、magic、seq、status bit0以及 ΔV 的有限正值条件。迟到包和重复包通过 seq 过滤。

## 7. 问题逐项答复

1. 模型 B 一轮仿真**总共调用 net_V 多少次**？能接受的总耗时上限是多少？

   **答复**　以当前 N=20 Greedy 推理为正式在线模式时，一条完整路线调用 760 次。按平均 RTT 1.1 ms 估算，通信与板端推理约为 0.836 s。加上外层策略计算后，建议把单实例验收上限设为 2 s。

   不同推理模式的调用预算如下。

   | 推理模式 | net_V 调用次数 | 按 1.1 ms 估算 |
   |---|---:|---:|
   | Greedy | 760 | 0.836 s |
   | Time-DP 单独处理一个固定顺序 | 2 128 | 2.341 s |
   | Greedy+Time-DP | 2 888 | 3.177 s |
   | Sample×128 | 97 280 | 107.008 s |
   | Sample×128+Time-DP | 99 408 | 109.349 s |
   | Sample×256 | 194 560 | 214.016 s |
   | Sample×256+Time-DP | 196 688 | 216.357 s |

   当前单样本串行UDP适合Greedy在线推理。多次采样需要后续增加批量协议、缓存或多流水并行。

2. 模型 B 跑在哪台机器、什么语言环境？板子和你的机器如何连接
   （直连/交换机）？IP 规划怎么定？

   **答复**　当前对接工程在Windows主机上运行，语言为Python 3，外层模型使用PyTorch。已经在`mrspp5090` Conda环境中完成本机模拟。首轮上板采用网线直连。主机网卡设置为`192.168.1.100/24`，ZCU104保持`192.168.1.10/24`，UDP端口为5000。交换机接入时继续使用同一子网，并保证板端MAC在多板环境下唯一。

3. 7 维输入是否保证在非奇异转移包络内？越界输入你们如何处理？

   **答复**　当前正式测试目标高度为400~600 km，倾角为65~70°，候选时间为1、9、17和25 d，小推力参数固定为0.0025。由此得到的h0、I0、Δh、ΔI、ΔΩ、fmax和tf均位于上述接口包络内。

   外部目标集合接入时，电脑端在UDP发送前执行包络检查。越界或非有限输入不发送至板端，并把对应目标时间动作设为非法。若当前层全部候选均被排除，则本次路线求解返回输入不可行错误。当前`sotosou`模拟代码已经检查板端返回值和通信状态，输入包络检查需要在接入任意外部目标库时启用。

4. 丢包/超时：接受"UDP + 你侧超时重发"的方案吗，还是需要换 TCP？

   **答复**　接受UDP加主机侧超时重发。直连环境的平均RTT约1.1 ms，建议单次等待上限设为50 ms，使用相同seq最多重发3次。3次重发耗尽后终止当前路线并记录层号、候选索引和seq。当前请求是幂等计算，使用相同输入和seq重发不会改变数学结果。现阶段保持UDP，无需切换TCP。

5. 是否需要"一轮开始/结束"的标记包（用于日志对齐和统计）？

   **答复**　算法运行不依赖开始或结束标记。首轮对接先保持现有协议。主机日志记录路线ID、开始时间、结束时间、760次请求的seq范围、重试数和超时数即可完成对齐。板端若需要按路线汇总耗时，可在后续协议版本中增加新的magic类型，现阶段不阻塞对接。

6. 应答里的 infer_us（推理微秒数打点）需要保留吗，还是精简应答？

   **答复**　保留`infer_us`。该字段可以区分板端PL推理耗时和UDP链路及主机处理耗时，便于核对826 µs推理预算、定位性能退化和统计真实上板结果。当前20 B应答开销很小，保留该字段更有利于验收。
